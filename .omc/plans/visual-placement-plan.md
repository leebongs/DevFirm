## 0. RALPLAN-DR 요약

### 원칙 (5)

- **P1. 그림은 산문이 못 하는 일을 할 때만 넣는다.**
  그림이 할 수 있고 문장이 못 하는 일은 넷뿐이다 — 위상(무엇이 무엇에 붙어 있나),
  순서(무엇이 먼저인가), 대비(둘이 어떻게 다른가), 분위기(거기 있으면 어떤 느낌인가).
  이 넷 중 하나에 해당하지 않으면 그림은 장식이고, 장식이 쌓이면 브로슈어가 된다.

- **P2. 라벨이 필요한 그림은 자산이 아니라 컴포넌트다.**
  A10 이 SVG 안의 한국어를 금지한다. 따라서 텍스트를 담아야 하는 다이어그램은
  "SVG 뼈대 + HTML 텍스트 오버레이"라는 결합 구조를 강요받는다(image-plan §0).
  그 결합은 320px 에서 어긋나고(A1), `content/*.ts` 가 바뀌어도 따라오지 않는다.
  **제약이 이미 답을 정해 뒀다** — 라벨 있는 그림은 컴포넌트 쪽 일이다.

- **P3. 재고를 먼저 쓴다.**
  일러스트 28개 중 **2개가 어디에도 쓰이지 않고 있다**(§부록 F-1). 놀고 있는 자산을
  둔 채 새로 그리는 것은 디자인 판단이 아니라 재고 관리 실패다.

- **P4. 바이트는 "무엇을" 만큼이나 "어디에" 의 문제다.**
  Lighthouse 는 5개 URL 만 측정한다. 같은 30KB 사진이 `/academy` 에서는 무해하고
  `/solutions` 에서는 남은 여유의 4분의 1을 먹는다.

- **P5. 실물이 있는 것은 실물로만 찍는다.**
  방문 가능한 공간(`/workspace`)을 생성 이미지로 보여주는 것은 톤의 문제가 아니라
  사실의 문제다. 입주 상담하러 온 사람이 그 방을 찾지 못한다.

기존 컴포넌트를 승급하고 놀고 있는 자산을 재배치한다. 신규 생성은 2점으로 묶는다.

| | |
|---|---|
| **얻는 것** | 절차 6곳·비교 1곳이 한 번의 컴포넌트 작업으로 동시에 개선. 신규 바이트 ≈ 30KB, 그것도 미측정 페이지에. 문구가 `content/*.ts` 에 남아 A10 무풍. 자산 재작업 리스크 0. |
| **잃는 것** | 페이지별 시각적 개성은 거의 늘지 않는다. `/services/*`·`/about/careers` 는 여전히 "글과 카드"로 남는다. 컴포넌트 승급은 **6곳을 동시에 바꾸므로** 잘못되면 6곳이 동시에 나빠진다(회귀 반경이 넓다). |
| **비용** | 컴포넌트 2건 수정 · 콘텐츠 스키마 2건 변경 · 신규 자산 2점 |

#### 선택지 B — 일러스트 확장

빈 섹션마다 개념도형을 생성한다(추정 8~12점).

| | |
|---|---|
| **얻는 것** | 페이지마다 고유한 그림이 생긴다. codex 파이프라인이 이미 검증됐고(23+5점 생성, 재작업 5건), 개념도형 배치는 **재작업 0건**이었다 — 성공 확률이 높은 경로다. |
| **잃는 것** | 8~12점 중 절반이 절차·목록 섹션인데, 그 자리는 라벨이 필수라 P2 의 결합 구조에 걸린다. 라벨 없이 그리면 "화살표가 있는 추상 도형"이 되어 아무것도 말하지 않는다. **그리고 `/solutions` 계열에 얹으면 D3 여유를 잠식한다.** |
| **비용** | 생성 8~12점 + 검수 + 레지스트리 8~12항목 |

#### 선택지 C — 사진 확장

빈 페이지마다 본문 사진을 넣는다(추정 6~10장).

| | |
|---|---|
| **얻는 것** | "조용한 정밀함"의 여백이 가장 빠르게 채워진다. 히어로 배너 8종이 이미 같은 방식으로 성공했다(§9). |
| **잃는 것** | **장당 30~45KB 가 그대로 바이트다.** `/solutions`(여유 131KB)·`/academy/courses`(708KB) 는 두세 장이면 임계에 닿는다. 더 결정적으로, 채워야 할 섹션 대부분이 *구조·절차* 섹션이라 사진이 설명을 대신하지 못한다 — 사진 위에 "다섯 단계"를 얹을 수는 없다. P5 에 걸리는 `/workspace` 도 여기서 해결되지 않는다. |
| **비용** | higgsfield 생성 6~10장 + 최적화 + 레지스트리 |

**권고: A.** B 와 C 는 무효가 아니라 **부분집합으로 흡수**된다 — A 는 B 에서 1점(개념도형),
C 에서 1장(사진)을 골라 넣는다. B·C 를 전면 채택하지 않는 이유는 취향이 아니라
D1(라벨 제약)과 D3(바이트 예산)이며, 둘 다 저장소에서 확인 가능한 사실이다.

## B. 자산 종류별 제작 방식

### 종류 1 — 컴포넌트 렌더 다이어그램 (T1)

**생성기**: 없음. `components/content/` 의 손으로 쓴 TSX.

**`StepFlow` 승급 명세** (`components/content/step-flow.tsx`)

현재는 `readonly string[]` 을 받아 번호 배지 + 문장 한 줄을 카드에 담고
`lg:grid-cols-4` 로 편다. 카드 사이에 아무 관계 표시가 없어 **순서가 아니라 목록으로
읽힌다.** 승급 요구:

| 항목 | 계약 |
|---|---|
| 입력 | `readonly string[]` **그리고** `readonly { title: string; desc?: string }[]` 둘 다 수용. 기존 5개 호출부는 손대지 않는다(하위 호환 필수 — 회귀 반경이 6곳이다) |
| 연결 | 단계 사이 연결선. `lg` 이상 가로, 미만 세로. **CSS 의사요소·보더로만** 그린다 — SVG 자산 아님, 바이트 0 |
| 마지막 항목 | 연결선 없음(`last:` 변형). 있으면 "다음이 더 있다"는 잘못된 신호 |
| 시맨틱 | `<ol>` 유지. 연결선은 의사요소라 접근성 트리에 올라가지 않는다(A5) |
| 반응형 | 320px 에서 세로 스택, 가로 스크롤 0 (A1) |
| 조판 | 모든 한국어 노드에 `break-keep` 유지 (A13) |
| 색 | 토큰만(`--border`, `--primary`). **배지를 현재의 `bg-primary/10 text-primary` 에서 채움형으로 바꾸면 `pnpm check:contrast` 재실행 필수**(A6) |
| 클라이언트 | `"use client"` 금지. 순수 서버 컴포넌트 (A11 — 화이트리스트는 닫혀 있다) |
| 문구 | 전량 `content/*.ts` 에 남는다 (A10) |

**콘텐츠 스키마 변경** (`content/_types.ts`)

```
ProcessStep = { title: string; desc?: string }
```
를 추가하고 `cic.roadmap.items`(T1-3)와 `staffing.difference`(T1-2)가 참조한다.
`services.software.process.steps` 등 기존 `string[]` 은 그대로 둔다 — 바꿀 이유가 없다.

**`ComparisonTable` 은 수정하지 않는다.** T1-2 는 컴포넌트가 아니라 **콘텐츠 형태**를
바꾸는 일이다: `staffing.difference.items`(현재 `{title, desc}[]` 4장)에서
좌변(프리랜서 직접 계약 시 무슨 일이 벌어지는가) 4문장을 새로 쓰고
`rows: { left, right }[]` 로 재구성한다. **좌변 문장은 지금 사이트에 존재하지 않는
새 카피이므로 사용자 검수 대상**(§부록 미결 Q-1).

**검증**: `pnpm check:content`(A10·A11) → `pnpm typecheck` → `pnpm test:e2e`
(responsive 320~1920 + axe) → 색 토큰을 건드렸으면 `pnpm check:contrast`.

## C. 단계

의존 순서로 묶었다. **Phase 1 이 실패하면 나머지는 착수하지 않는다** — 여섯 자리를
동시에 바꾸는 작업이라 회귀 반경이 가장 넓다.

### Phase 0 — 저장소 위생 (선행, 30분)

세 건의 문서·설정 불일치를 먼저 닫는다. 이후 단계가 전부 이것들에 의존한다.

- `package.json` 에 `"gen:photo"` 추가 (F-2)
- `scripts/preview-illustrations.mjs` 기본 대상 배열에 `"concept"` 추가 (F-3)
- `illustrations.home` 처리 결정 (F-1 — 아래 §E 참조)

**종료 조건**: `pnpm gen:photo` 와 `pnpm preview:art` 가 각각 실행되어
기존 14장·28점을 정상 처리하고, `pnpm verify` 통과.

### Phase 1 — `StepFlow` 승급 (T1-1, T1-3)

컴포넌트 수정 → `content/_types.ts` 에 `ProcessStep` 추가 → `cic.roadmap` 재구성 →
6개 호출부 확인.

**종료 조건** (전부 충족해야 Phase 2 착수):
- 기존 5개 `string[]` 호출부가 **코드 변경 없이** 계속 렌더된다
- `pnpm check:content` 통과 — `"use client"` 파일 수가 **변하지 않는다**
- `pnpm test:e2e` 통과 — 320px 가로 스크롤 0, axe critical/serious 0
- 색 토큰을 건드렸다면 `pnpm check:contrast` 통과
- 6개 라우트를 실제로 렌더해 **연결선이 마지막 항목 뒤에 남아 있지 않은지** 눈으로 확인
  (`lg:grid-cols-3`·`lg:grid-cols-2`·기본 4열 — 열 수가 호출부마다 다르므로
  줄바꿈 지점에서 연결선이 허공을 가리킬 수 있다)

### Phase 2 — 비교표 전환 (T1-2)

`staffing.difference` 좌변 4문장 신규 작성 → `rows` 재구성 → `ComparisonTable` 로 교체.

**종료 조건**: 좌변 카피 **사용자 검수 완료**(Q-1). 320px 에서 행이 위아래로 쌓이고
가로 스크롤 0. `pnpm verify` 통과.

### Phase 3 — 기존 자산 재배치 (T2-1 ~ T2-5)

다섯 건이 서로 독립이라 병렬 가능. T2-5 만 성격이 달라 마지막에 둔다.

**종료 조건**:
- 다섯 자리 모두 레지스트리에서 치수를 전개했고 하드코딩 0
- **T2-5 후 `/contact` 의 `total-byte-weight` 가 1,000,000 바이트 미만**
  (`lhci autorun` 또는 `--url` 한정 수집으로 실측)
- axe 0, CLS ≤ 0.1 유지

### Phase 4 — 신규 생성 2점 (T3-1, T3-2)

Phase 1~3 이 게이트를 흔들지 않았음이 확인된 뒤에만 착수한다. 생성물은 되돌리기가
가장 비싸므로 마지막이다.

**종료 조건**:
- T3-1: `.preview/concept.png` 시트에서 기존 5점과 나란히 놓고 **획 굵기·모서리 반경·
  투영이 어긋나지 않음**을 확인. 흰/Mist 양쪽 생존. ≤20KB, 팔레트 이탈 0, 내부 한국어 0
- T3-2: 얼굴 식별 불가, 팔레트 밖 색 없음(있으면 `tone` 으로 눌림), AVIF ≤ 45KB
- 레지스트리 치수 = 스크립트 출력 실측치
- `/academy` 렌더 후 CLS ≤ 0.1

| **A7** `total-byte-weight` | warn @ 1MB | **`/` 2087KB · `/contact` 1201KB 초과.** `/solutions` 845KB(여유 131KB) · `/academy/courses` 708KB · `/solutions/agents/construction` 691KB | **`/contact` 1201KB → 약 809KB (임계 아래로 회복)**, 나머지 변화 없음 | T2-5 가 Google Maps JS 355KB + Roboto 37KB 를 제거한다. 신규 사진은 측정 URL 이 아닌 `/academy` 에만 얹는다. **T2-1~4 는 이미 저장소에 있는 SVG 라 신규 다운로드가 아니지만, 해당 페이지 기준으로는 새 요청이다** — `agentPipeline`(≈2KB)·`twoAxes`(≈2KB)·`risk`(≈2KB) 수준이라 어느 페이지에서도 유의미하지 않다. **`/` 2087KB(히어로 영상)는 이 계획이 손대지 않으므로 그대로 warn 을 유지한다** |
| **A8** 초기 JS | ≤ 130KB/페이지 | 통과 | **변화 없음 또는 감소** | 신규 클라이언트 컴포넌트 0. T2-5 는 `/contact` 에서 `MapEmbed` 를 제거해 오히려 줄어든다. `tests/e2e/bundle.spec.ts` 로 확인 |
| **A5** 접근성 | axe critical/serious 0 | 통과 | **변화 없음** | `StepFlow` 는 `<ol>` 유지, 연결선은 의사요소라 접근성 트리 밖. `ComparisonTable` 은 이미 검증된 컴포넌트. 신규 자산 2점은 `alt` 필수 타입에 걸린다. `tests/a11y/axe.spec.ts` |
| **A10** 콘텐츠 분리 | 한국어는 `content/*.ts` 에만 | 통과 | **변화 없음** | 신규 SVG 안에 한국어 없음, alt 는 레지스트리, `staffing.difference` 좌변 신규 카피도 `content/services.ts`. `pnpm check:content` |
| **A11** 클라이언트 경계 | 화이트리스트 초과 시 실패 | 통과 (11개 등록) | **변화 없음** | 계획 전체에서 `"use client"` 신규 0. 검사는 **초과만** 막으므로(누락은 통과) 화이트리스트 파일을 수정할 일이 없다 |
| **A1** 반응형 | 320~1920 가로 스크롤 0 | 통과 | **재검증 필수** | `StepFlow` 연결선과 `ComparisonTable` 전환이 가장 위험한 두 지점. `tests/e2e/responsive.spec.ts` 6뷰포트 |
| **A13** 한국어 조판 | `keep-all` | 통과 | **변화 없음** | 승급된 `StepFlow` 의 `title`·`desc` 양쪽에 `break-keep` 유지 |

### A7 바이트에 대한 판단

이 계획은 **바이트를 순감소시킨다.** 신규 래스터 1장(약 30KB)을 측정 대상이 아닌
페이지에 얹고, 측정 대상인 `/contact` 에서 392KB 를 걷어낸다.

다만 정직하게 적어 두면 — `total-byte-weight` 는 `warn` 이지 `error` 가 아니다
(`lighthouserc.json` 확인). `/` 의 2087KB 는 CI 를 깨뜨리지 않고 있으며 이 계획도
그것을 고치지 않는다. **`/contact` 회복은 부수 효과이지 이 계획의 목적이 아니다.**
목적은 그 페이지에서 실제로 놀고 있는 자산이 하나 있었다는 것이다.

### 측정 범위에 대한 권고 (선택)

이 계획이 바꾸는 페이지 중 **LH 가 측정하는 것은 `/solutions` 와 `/contact` 뿐**이다.
`/services/staffing`·`/academy`·`/about/cic` 는 측정되지 않으므로 회귀가 나도 CI 가
모른다. `lighthouserc.json` 의 `collect.url` 에 `/services/staffing` 과 `/academy` 를
추가할 것을 권고하되, **먼저 로컬에서 수집해 두 페이지가 전 카테고리 ≥95 를 만족하는
것을 확인한 뒤에만 커밋한다** — 통과를 확인하지 않고 URL 을 늘리면 CI 가 깨진다.

## ADR (초안 — 검토 후 확정)

- **결정**: 시각 자산 확충을 *생성*이 아니라 *컴포넌트 승급 + 기존 자산 재배치*로
  수행하고, 신규 생성은 2점(개념도형 1 · 사진 1)으로 제한한다.
- **동인**: D1 A10 라벨 제약 · D2 `StepFlow` 6곳 공유 · D3 LH 바이트 예산.
- **검토한 대안**: 선택지 B(일러스트 8~12점 확장) · 선택지 C(사진 6~10장 확장).
- **채택 이유**: B·C 가 채우려는 자리의 다수가 절차·목록 섹션이며, 그 자리는 A10 때문에
  구조적으로 컴포넌트의 영역이다. B·C 는 무효가 아니라 A 의 부분집합으로 흡수됐다.
- **결과**: 여섯 절차 섹션이 동시에 개선되지만 **회귀 반경도 여섯 곳**이다 →
  Phase 1 을 단독 관문으로 두고 종료 조건을 통과하지 못하면 나머지를 착수하지 않는다.
  `/contact` 는 임계 아래로 회복하나 `/` 는 warn 을 유지한다.
- **후속**: F-4·F-5 문서 정합성 · `/workspace` 실촬영(Q-4) · LH 측정 URL 확대.
